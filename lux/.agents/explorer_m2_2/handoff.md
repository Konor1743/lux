## 2. Logic Chain

1. From **Observation 1 & 5**, `create_stream/2`, `update_stream/2`, and `list_streams/2` require interaction with multiple resource parts. The default query parameter `part=snippet,cdn,status,contentDetails` ensures callers receive complete stream metadata, including ingestion endpoints and health status, without manual part specification.
2. From **Observation 2**, `Client.request/3` handles all low-level HTTP transport, authentication headers, JSON body serialization, and error mapping. `LiveStreams` functions can delegate directly to `Client.post/2`, `Client.get/2`, `Client.put/2`, and `Client.delete/2` by passing normalized query parameters and JSON payloads.
3. From **Observation 1 & 5**, developers creating streams often pass flat maps (e.g. `%{title: "Stream", resolution: "1080p", ingestion_type: "rtmp"}`) rather than deeply nested JSON. Normalizing inputs in `build_create_body/1` and `build_update_body/1` supports both flat shortcut keys and canonical YouTube schema structures with automatic fallback defaults.
4. From **Observation 1**, `get_stream/2` is specified to return `{:ok, stream}` rather than a list response. Since `GET /liveStreams?id=...` returns `%{ "items" => [stream] }`, `get_stream/2` unwraps the single stream map `hd(items)` or returns `{:error, :not_found}` when `items: []`.
5. From **Observation 2 & 1**, `DELETE /liveStreams?id=...` returns HTTP 204 with body `""`. Returning `{:ok, %{id: id, deleted: true}}` on success satisfies the contract `{:ok, map()}`.
6. From **Observation 3 & 4**, unit tests using `UnitAPICase` can intercept requests via `Req.Test.expect(YouTubeClientMock, fn conn -> ... end)` and verify URL query parameters (`part`, `mine`, `id`, `maxResults`), JSON body structure (`snippet`, `cdn`, `contentDetails`), and HTTP verbs (`GET`, `POST`, `PUT`, `DELETE`).

## 3. Caveats

- **YouTube API Rate & Quota Limits**: Creating and deleting streams consumes YouTube Data API quota units. In production, reusable streams (`isReusable: true`) should be preferred over creating new streams for every broadcast.
- **`ingestionInfo` Availability**: Ingestion addresses and stream keys are generated by YouTube upon creation and cannot be updated via `PUT /liveStreams`.
- **Live Video Ingestion Protocols**: While YouTube supports `"rtmp"`, `"dash"`, and `"hls"`, `"rtmp"`/`"rtmps"` is the de facto standard for video encoders (OBS/FFmpeg).
- **Network Mode**: In CODE_ONLY mode, all test execution relies strictly on `Req.Test` plugs with zero external network connectivity.
